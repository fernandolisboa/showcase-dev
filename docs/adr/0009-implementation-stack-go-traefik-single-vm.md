# Implementation stack: Go control plane + React UI, shell-out Compose orchestration, Traefik proxy, single Azure VM

The control-plane programming language has **no decision-relevant effect on Session spin-up**: issuing the handful of Docker API calls that start a Stack costs ~20–50 ms against a multi-second boot dominated by the container runtime (`dockerd→containerd→runc` ~600–800 ms), gVisor sentry init, the Project's own app cold-boot, and the DB seed. A fast-spin-up priority is therefore neutral across languages, so the stack is chosen for **low operational surface for a solo maintainer** and **founder comfort**, with every mechanism kept boring and behind the ADR-0001 Runner seam.

## The stack

- **Control plane — Go** (the HTTP API + the Runner), **React (Vite + TypeScript)** for the Owner admin and Portfolio pages, **Postgres** for the write model. The React build is embedded into the Go binary via `go:embed`, so a deploy is a single dependency-free artifact. Go is chosen because the whole substrate it drives — Docker, containerd, gVisor, Traefik — is Go-native, it compiles to one static binary, and once host devops is a Linux VM either way (below) the founder's .NET fluency saves nothing operationally here; its small learning cost was accepted explicitly. React over Angular: lower ceremony for a small UI maintained solo, and a larger corpus for AI-assisted development.
- **Orchestration — generate a locked-down Compose file per Session and shell out to the `docker compose` v2 CLI**, behind the ADR-0001 Runner interface. `up -d --wait` gates readiness on healthchecks (ADR-0004); `down -v` keyed by the project name `s-<sessionId>` is the whole lifecycle handle; `ps`/`inspect`/`logs` (`--format json`) supply ADR-0006's failure facts. The generated Compose bakes in every ADR-0002/0003 invariant structurally — `runtime: runsc`, `mem_limit`/`cpus`/`pids_limit`, isolated per-Session network, non-root, read-only rootfs, no Docker socket — reinforced by `default-runtime: runsc` in the host daemon so gVisor can never be omitted. Shelling out keeps the Go dependency footprint tiny and every failure reproducible by hand.
- **Reverse proxy — Traefik v3.** A single wildcard cert `*.run.showcasedemo.app` via ACME **DNS-01 on Cloudflare** (built into Traefik, no recompile). Routes are driven by the **HTTP provider** — the Go control plane serves the `sessionId→backend` map that Traefik polls, which is exactly ADR-0004's "the Runner keeps the proxy's map current." The proxy is **attached to each Session's bridge network at provision and disconnected at teardown**, reaching the Stack over its isolated network (ADR-0007) rather than via published host ports.
- **Host — a single Azure Linux VM (IaaS)** running Docker + gVisor, with the Go control plane, Runner, Traefik, and the publish-time image build/cache all co-located. The control plane reaches Docker over the **local socket only**, never exposed remotely. Vertical scale first, under the global concurrency cap (ADR-0006). Platform secrets (the GitHub App key, ADR-0008; per-Stack DB creds) live in Azure Key Vault and never enter a demo (ADR-0003).

## Considered options

- **.NET or Node for the control plane** — rejected: spin-up is latency-neutral, so neither beats Go's container-native fit and single-binary ops. `.NET`'s `Docker.DotNet` SDK is abandoned (last release 2023; upstream declared inactive) — moot under shell-out but a signal — and once the host is a VM either way, .NET fluency buys nothing operationally. Node is fluency-adjacent but splits the control plane from nothing it gains.
- **Angular for the UI** — rejected: its enforced structure pays off at team/enterprise scale, not for a solo-maintained admin and a few pages; the verbosity is a standing tax.
- **In-process Compose SDK (`github.com/docker/compose/v2`) now** — deferred, not rejected. It is the steady-state low-ops option *for a maintained library that cannot assume the `docker compose` binary is installed* — a constraint that does not transfer to a single controlled VM. For a Go beginner it adds a large Docker-internal dependency with no API-stability guarantee. It is the documented upgrade, via the Runner seam, if structured failure events (ADR-0006) ever justify it.
- **Raw Engine-API orchestration** — rejected: reimplements Compose's dependency ordering and healthcheck gating for no MVP gain.
- **Caddy** — rejected: wildcard DNS-01 requires a custom `xcaddy` build with a `caddy-dns` plugin — a permanent maintenance chore — whereas Traefik ships DNS providers in-binary and its HTTP provider matches the control-plane-owned route map.
- **Published host ports for proxy→Session routing** — rejected: weaker isolation and port bookkeeping versus attaching the proxy to each Session's isolated network.
- **Managed container PaaS (Azure Container Apps / ACI / App Service)** for the host — rejected: cannot run the `runsc` custom runtime. microVMs (Kata/Firecracker) and multi-node remain deferred (ADR-0002, SEED §14).

## Consequences

- Guest-felt spin-up latency is owned by the **Project's own image, app cold-boot, and seed** plus gVisor — not by anything in this stack. The levers are baking the seed into the image (turns seconds into milliseconds), fast app boot, a 1–2 s healthcheck interval, and the pre-issued wildcard cert.
- The ADR-0001 Runner interface remains the single swap point for every future orchestration or isolation upgrade (in-process Compose; later Kata/Firecracker per ADR-0002) — none of which touch routing, the run contract, or demo links.
- The **"booting…" page is control-plane-owned**: no proxy renders a holding page for a not-yet-listening backend, so the Runner points the proxy's route at a control-plane splash endpoint until `--wait` succeeds, then flips it to the live Stack — the Guest still sees the proxy serve a "booting…" page (ADR-0004), now sourced from the control plane.
- Operating one VM means one box to harden and patch, and the Docker socket never leaves it. Founder Azure familiarity (Key Vault especially) carries the secrets boundary even though VM provisioning itself is new — and that provisioning is ~90% generic Linux + Docker, written down once.
- If the control plane ever moves to driving the Docker Engine API directly (rather than shelling out), depend on the maintained `Docker.DotNet.Enhanced` (Testcontainers fork), not the dead upstream `Docker.DotNet` — recorded so the trap is not re-discovered. (Not applicable while the control plane is Go and shells out.)
